## 目标和判断

以《本地服务监控 · PRD 与开发计划》为准，对当前构建逐条跑 V1 验收，修复不通过的项，再做 PRD 中的应用内存视图。这是在上游基础上的二次开发，不从零重写：上游 README 声明 MIT，PRD 中“许可不允许就重写”的风险不成立。

对照后发现，PRD 的 MVP 大部分上游已经具备，包括服务列表、清理、按应用汇总内存、内存条。因此不再做 V0 脚本验证，而是直接用真实构建做验收。另外需要说明：悬停内存条查看单个应用内存是上游已有的功能，不是本 Fork 新增的。

## 实现

- **扫描过滤**：进程名带点号版本号（如 `python3.13`）时，去掉版本号再匹配白名单。位于 `.framework/` 内的 `Python.app` 启动壳和 Xcode 工具链不算作应用内嵌后端。
- **启动器识别**：从监听进程往上找用户实际运行的命令时，遇到监听其他端口的父进程就停止，避免把启动它的工具当成同一个服务。
- **Homebrew 服务**：根据 launchd 标签识别，同时支持新前缀 `sh.brew.*` 和旧前缀 `homebrew.mxcl.*`。识别出的服务与数据库同样受保护（不进清理，不发告警），停止和重启都走 `brew services`；列表悬停按钮对它们不显示停止。redis 会用进程标题覆盖环境变量，所以不读 `XPC_SERVICE_NAME`，改为查询 launchd。
- **Socket 扫描**：用 libproc（`proc_pidinfo`、`proc_pidfdinfo`）直接读每个进程的 TCP 连接，取代 lsof，并保持 lsof 的结果语义：共享同一 socket 时取进程号最小者；地址格式与 lsof 相同；进程名取自 `proc_name`。
- **性能**：
  - 应用归属按“进程号 + 启动时间”缓存；
  - Claude Code 会话标题改为增量读取新增内容，只处理完整的行；
  - `launchctl` 每轮扫描最多调用一次；
  - 其他应用的内存只在面板打开时刷新，关闭后每 30 秒刷新一次。
- **应用内存页**：入口是图例中的“其他应用”，以及内存条上的应用段。口径与活动监视器“内存”列一致，包含压缩内存，所以合计可能大于列表页的“其他应用”，页面上有说明文字。

## 验证

- **测试**：23 项全部通过，新增的测试覆盖扫描过滤、启动器识别、launchd 标签解析、会话记录的增量读取（包括写了一半的行）。
- **Socket 扫描等价性**：新旧扫描器并排运行 5 轮，31 个监听端口和 124 个有连接的端口逐项一致；单次扫描从 41 ms 降到 3.6 ms。
- **应用汇总**：加缓存前后都是 204 个应用，归属完全相同；单次从 26 ms 降到 6.7 ms。
- **会话标题**：本机近 3 天 140 份真实会话记录，新旧逻辑算出的标题和目录全部一致。
- **brew 服务**：
  - 用仿真的 launchd 任务确认：直接发信号后，launchd 在 3 秒内会重新拉起进程；修复后停止操作走 brew，不再直接发信号。
  - 对 redis 做了一次真实的停止和恢复：`brew services stop` 1.7 秒返回成功，5 秒内未被重新拉起；随后用 `brew services start` 恢复，`redis-cli ping` 返回 PONG。恢复后标签变为新前缀 `sh.brew.redis`，这是 Homebrew 自身的行为。
- **界面**：确认区、失败状态、应用页和列表页都渲染了中英文截图检查。应用页第一版有两个问题：各项加起来与顶部合计对不上；图例把列表页撑宽、右侧被截断。两者都已修复。
- **面板打开检测**：用临时构建自动开关面板，确认每次打开和关闭都能被检测到；检测代码已撤掉。
- **CPU**：稳定运行时三轮实测分别为 0.88%、0.92%、1.13%。波动主要来自本机临时进程的变化。
